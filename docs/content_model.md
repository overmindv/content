# Content model

`content` хранит самостоятельные контентные документы и их версии.

Сервис не владеет каталогом, пользователями, ролями, заданиями, обсуждениями и review workflow. Другие сервисы могут ссылаться на контент через `content_item.id`, но `content` не хранит связи с вузами, программами, курсами или темами.

## Основные сущности

### ContentItem

Основная карточка контентного документа.

Типы:

- `article`
- `note`
- `summary`
- `theory`

Статусы:

- `draft`
- `published`
- `archived`

Поля:

```text
id
type
status
title
slug
description
current_revision_id
published_revision_id
created_by
updated_by
created_at
updated_at
published_at
archived_at
```

`created_by` и `updated_by` являются opaque user id. `content` не знает модель пользователя и не проверяет роли.

### ContentRevision

Версия тела документа.

Форматы:

- `markdown`
- `typst`

Поля:

```text
id
content_item_id
revision
format
source
source_hash
message
created_by
created_at
```

Каждый `ContentItem` может иметь много ревизий. Пара `content_item_id + revision` должна быть уникальной. Новая ревизия становится текущей через `current_revision_id`.

`source` хранит исходный Markdown/Typst. `source_hash` нужен для проверки изменения тела документа и идемпотентности будущих операций.

### Tag

Тег, принадлежащий контентному домену.

Поля:

```text
id
name
slug
created_at
```

Теги нужны для базовой группировки и поиска по контенту внутри `content`. Если позже появится глобальный сервис таксономии, `tags` можно будет заменить или синхронизировать с ним.

### ContentTag

Связь многие-ко-многим между документами и тегами.

Поля:

```text
content_item_id
tag_id
created_at
```

### ContentAsset

Ссылка на внешний файл или медиа-объект.

Типы:

- `image`
- `attachment`
- `pdf`
- `archive`

Поля:

```text
id
content_item_id
revision_id
asset_id
kind
title
position
created_at
```

`asset_id` является внешним id файла из media/file сервиса. `content` не хранит бинарные файлы.

`revision_id` опционален: asset может относиться ко всему документу или к конкретной ревизии.

## Написание статей в MVP

В MVP статья использует существующие `ContentItem` и `ContentRevision`, отдельная сущность `Article` не создаётся.

Для сценария написания статьи действуют следующие ограничения:

- `ContentItem.type` всегда равен `article`;
- новая статья всегда создаётся в статусе `draft`;
- редактор работает только с форматом `markdown`;
- исходный Markdown хранится в `ContentRevision.source` и является единственным источником текста статьи;
- HTML, полученный при предпросмотре, не хранится в `content`;
- авторизация и проверка прав выполняются API Gateway, а `content` получает opaque user id доверенного вызывающего сервиса;
- публичное чтение использует только `published_revision_id`, редактор использует `current_revision_id`.

### Создание пустого черновика

1. Автор выбирает создание новой статьи.
2. API Gateway определяет автора по JWT и вызывает `content` с его user id.
3. `content` создаёт `ContentItem` с типом `article` и статусом `draft`. Переданный клиентом статус не используется.
4. Пустые `title`, `description` и `source` допустимы для черновика.
5. Если slug не передан, сервис создаёт стабильный технический slug. Slug не является пользовательским полем редактора MVP.
6. Одновременно создаётся первая `ContentRevision`: `revision = 1`, `format = markdown`, `source = ""`.
7. `current_revision_id` указывает на первую ревизию, а `published_revision_id` и `published_at` остаются пустыми.
8. Созданный идентификатор возвращается автору и используется для открытия редактора.

Создание карточки и первой ревизии выполняется в одной транзакции: частично созданного черновика быть не должно.

### Открытие существующего черновика

1. API Gateway проверяет аутентификацию и право пользователя редактировать статью.
2. Gateway запрашивает статью по `content_item.id` через внутренний API.
3. `content` возвращает карточку и ревизию из `current_revision_id`.
4. Редактор запоминает полученный `current_revision_id`; он потребуется при следующем сохранении.
5. Если статья не существует, возвращается `NotFound`.

Черновики доступны только через внутренний авторский API. Публичный API не должен позволять отличить отсутствующую статью от существующего черновика.

### Сохранение новой ревизии

1. Редактор передаёт `content_item_id`, Markdown в `source` и `expected_current_revision_id` — ревизию, на основе которой выполнялось редактирование.
2. `content` в транзакции блокирует карточку статьи и сравнивает `expected_current_revision_id` с фактическим `current_revision_id`.
3. Если идентификаторы различаются, сохранение отклоняется. Серверный текст не перезаписывается, а клиент получает конфликт версии.
4. Если `source_hash` совпадает с hash текущей ревизии, сервис возвращает текущую ревизию и не создаёт дубликат.
5. Иначе создаётся следующая ревизия с номером `MAX(revision) + 1`.
6. `current_revision_id` переключается на новую ревизию, `updated_by` и `updated_at` обновляются.
7. `published_revision_id` при обычном сохранении не изменяется.

Сохранение разрешено для нового черновика и для редактирования уже опубликованной статьи. Во втором случае читатель продолжает видеть прежнюю опубликованную ревизию.

### Первая публикация

1. Редактор передаёт `content_item_id` и `expected_current_revision_id`.
2. `content` блокирует статью и убеждается, что текущая ревизия не изменилась.
3. Сервис проверяет обязательные для публикации поля.
4. `published_revision_id` устанавливается равным `current_revision_id`.
5. Статус меняется с `draft` на `published`.
6. `published_at` устанавливается в текущее время.
7. Публичный API начинает возвращать именно опубликованную ревизию.

Изменение статуса через обычное обновление карточки запрещено. Публикация является отдельной доменной операцией.

### Редактирование и повторная публикация

1. После первой публикации автор может создать новую текущую ревизию.
2. Статус карточки остаётся `published`, а `published_revision_id` продолжает указывать на прежний текст.
3. Публичный API продолжает возвращать прежнюю ревизию до следующей публикации.
4. При повторной публикации `published_revision_id` переключается на новую `current_revision_id`.
5. Первая дата `published_at` сохраняется; `updated_at` отражает последнее изменение статьи.
6. Повторная публикация уже опубликованной ревизии идемпотентна: новая ревизия не создаётся и состояние не изменяется.

### Доступность по статусам

| Статус | Доступен редактору | Доступен публично | Можно сохранить ревизию | Можно опубликовать |
| --- | --- | --- | --- | --- |
| `draft` | да | нет | да | да, после валидации |
| `published` | да | да, только `published_revision_id` | да | да |
| `archived` | через внутренний API | нет | нет | нет |

Для публичного запроса `draft`, `archived` и документ без `published_revision_id` считаются отсутствующими и приводят к `NotFound`.

### Обязательные поля при публикации

- непустой `title` после удаления пробелов по краям;
- `title` не длиннее 256 символов;
- существующая текущая ревизия;
- непустой `source` после удаления пробелов по краям;
- `format = markdown` для сценария написания статей MVP;
- актуальный `expected_current_revision_id`.

`description`, теги и assets для публикации необязательны.

### Ошибки gRPC API

| Операция или условие | gRPC-код | Поведение клиента |
| --- | --- | --- |
| Некорректный ID, тип, формат или другое поле запроса | `InvalidArgument` | Исправить запрос, повтор автоматически не выполнять |
| Статья или ревизия не существует | `NotFound` | Закрыть редактор или показать, что статья удалена |
| Публичный запрос черновика или архивной статьи | `NotFound` | Не раскрывать существование непубличного документа |
| Slug уже занят другой статьёй | `AlreadyExists` | Запросить или сгенерировать другой slug |
| `expected_current_revision_id` не совпадает с текущей ревизией | `FailedPrecondition` | Сохранить локальный текст и предложить разрешить конфликт |
| Публикация без заголовка, текста или текущей ревизии | `FailedPrecondition` | Показать недостающие условия публикации |
| Сохранение или публикация архивной статьи | `FailedPrecondition` | Запретить операцию до отдельного восстановления из архива |
| Пользователь не аутентифицирован | `Unauthenticated` на уровне API Gateway | Запросить вход в систему |
| Пользователь не может редактировать статью | `PermissionDenied` на уровне API Gateway | Не вызывать внутреннюю операцию `content` |
| PostgreSQL временно недоступен | `Unavailable` | Разрешить безопасный повтор запроса |
| Неожиданная внутренняя ошибка | `Internal` | Не раскрывать детали, записать ошибку в лог |

Повтор неизменившегося сохранения и повторная публикация текущей опубликованной ревизии являются успешными идемпотентными операциями, а не ошибками.

## Инварианты

- У документа всегда есть `id`, `type`, `status` и `slug`; пустой `title` допустим только у черновика.
- `slug` уникален внутри `content`.
- У документа может быть много ревизий, но только одна текущая ревизия.
- У статьи в authoring MVP всегда есть текущая ревизия, в том числе у пустого черновика.
- У публично доступного документа обязательно есть `published_revision_id`.
- `published_revision_id` не меняется при сохранении новой текущей ревизии и изменяется только при публикации.
- Удаление документа удаляет его ревизии, связи с тегами и asset references.
- Файлы, пользователи, курсы, темы, задания и обсуждения принадлежат другим сервисам.

## Не входит в модель MVP

- metadata-таблица для языка, сложности, reading time и SEO
- связи с вузами, программами, курсами и темами
- роли и права пользователей
- задания, тесты, решения и подсказки
- комментарии, обсуждения и споры
- pull request / review workflow
- WYSIWYG и Live Preview внутри редактора
- raw HTML в Markdown
- совместное редактирование и автоматическое объединение конфликтов
- серверное автосохранение при каждом вводе
- сравнение и восстановление ревизий в пользовательском интерфейсе
- backlinks, transclusion, outline и граф связей как в Obsidian
- загрузка изображений и файлов из редактора
- подсветка синтаксиса, формулы, диаграммы и расширения Markdown
- отложенная публикация и расписание
- отдельный редактор Typst
